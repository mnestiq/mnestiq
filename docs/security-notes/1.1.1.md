# Security note: a file named like the pinned key was trusted in its place (mnestiq 1.1.1)

Published 2026-11-15.

**In short:** `mnestiq verify --trusted-key` and `mnestiq dashboard --trusted-key` tried their argument as a
file name before they read it as a key. If the folder the command was run in held a file whose name was the
text of your public key, the key inside that file was the one trusted. Evidence signed by someone else then
verified as VALID under your pin. We found this in our own testing. Nobody reported it, and we know of no use
of it. Upgrade to 1.1.1.

**Affected:** every release from 0.1.0 to 1.1.0, on the command line. The Python call `verify_file` takes
the key as text only and was not affected.

## What was wrong

A pinned key is what makes a verdict say who signed a file, and not only that the file is consistent. You
give it as base64 text, or as the path of a `.pub` file. The code that read the argument asked first whether
a file of that name exists, and read the file if one did.

So the text of a key could itself be a file name. Someone who could put a file into the folder you ran the
command in could name it after your public key and put a public key of their own inside. A public key is
not a secret, so the name is known. From then on:

    mnestiq verify evidence.jsonl --trusted-key <your key>

trusted their key and not yours. A file they had written and signed from the first record to the last
verified as VALID, and the output named no other key than the one you typed.

The folder is the weak point. A folder of evidence that another party sends you, an unpacked archive, or a
shared folder are all places where someone else decides which files exist. Running `verify` from inside
such a folder was enough.

Two details:

- A key with a `/` in its base64, which is about half of all keys, needs a folder named after the part
  before the `/` and a file named after the rest. Whoever can add a file can add a folder.
- The same held for a key in a wrong spelling, such as without its `=` at the end. Such text was refused
  when no file had that name, and read as a file when one had.

## What it did not do

- Nothing happened unless a file or folder of that exact name was in the folder the command was run in.
- No signature was forged, and no evidence file was changed. The fault was in which key was trusted.
- `mnestiq verify` without `--trusted-key` was not made weaker. It has always said that no key is pinned.
- A key given as the path of a `.pub` file was read from that file, as intended. Whoever can replace that
  file chooses the key, which was true before and is true now. Keep it where others cannot write.
- `verify_file` and `ChainVerifier` take keys as text only and were not affected.

## How to check whether it touched you

Look in the folders you ran `mnestiq verify` or `mnestiq dashboard` from, and in the evidence folders
others sent you, for a file or folder whose name is your public key or the start of it. If there is none,
and none was there when you verified, the fault was not used against you. If you cannot say what was there
at the time, verify the evidence again with 1.1.1.

## What changes in 1.1.1

- **A pinned key given as text is never opened as a file.** The argument is opened as a file only when it
  is written as a path: a name that ends in an extension, such as `signing.pub` or `keys/signing.pub`, or
  one that starts with `./` or `../`.
- Text that starts with a key is the key, whatever comes after it. `<key>.pub` is not a path.
- A key must be the base64 of its bytes in the one canonical spelling. Space and a line end around it are
  accepted. Any other spelling is refused, with a message that says how to give a file.
- **A key file whose name has no extension must now be given as `./name`.** This is the one thing that
  can break a command that worked before.

Mnestiq Workbench reads `--trusted-key` and `config set trusted-key` with the same code, so 0.3.0 and
earlier are affected in the same way. Use the Workbench release that requires mnestiq 1.1.1.

## Also in this release

Found in the same round of testing. None of them let a changed signed value verify as VALID.

- A number now has one accepted spelling, the one canonical JSON gives it. The 1.1.0 note listed the
  respelling of a number as a known limit: `4100.0` for `4100` left the hash the same, while another
  program could read another value. Such a line is now refused. Every release of the recorder has written
  numbers in this spelling, so no file a recorder wrote is affected.
- A salt is held to its 16 bytes wherever its digest is checked. Before, a verifier made without the
  schema let a byte move between a salt and its value under the same digest.
- `mnestiq inspect` prints the warnings `mnestiq verify` gives, says after which record no checked
  signature covers what it lists, and no longer prints "signed by" for a checkpoint it did not check.
- A recorder changes nothing in a file it refuses to continue.

The changelog has every change.

## Known limits

These remain:

- A name that ends in an extension is a path. If you give a key with something before it and an extension
  after it, such as `'<key>'.pub` or `key=<key>.pub`, and a file of that name exists, the file is read.
  Give the key as the key, or the file as a path you chose.
- A genuine key file whose path starts with text that has the form of a key is refused. Give it with `./`
  before it. On Linux and macOS this can also happen to an absolute path, where `./` does not fit: give
  that file by a relative path.
- A pin is only as good as the place it comes from. Take the public key from the people who run the
  agent, over a channel the sender of the evidence does not control.
- The limits in `docs/threat-model.md` and in the 1.1.0 note still apply, with the one on respelled
  numbers now closed.

## What to do

Upgrade. Give the key as text, or as the path of a `.pub` file in a folder only you write to. Do not run
`mnestiq verify` from inside a folder someone else filled without looking at what it holds. If you pinned a
key by text while standing in such a folder, verify that evidence again with 1.1.1.
