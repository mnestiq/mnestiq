# Security note: crafted evidence files, and what our own testing found (mnestiq 1.1.0)

Published 2026-11-09.

Thanks to Agentic Thinking, who privately reported the problems that started this work.

**In short:** a crafted line in an evidence file could crash `mnestiq verify`, and a damaged record could
make the detection rules lose findings without saying so. We then tested every other part of the recorder
in the same way and found more. In our tests, without the signing key or a signing identity, no change to a
value in a signed record stayed VALID under a pinned key. Respelling a number or changing JSON spacing does not
change a record's hash, and the last checkpoint's timestamp can be removed (see "Known limits").

Other routes can end in VALID. In 1.0.1 and earlier, the spare bits of the last signature could be changed
without the key, which is fixed. Redacting a changed file could too, which is also fixed. A recorder can carry on
from a file whose unsigned end was rewritten: `mnestiq verify` now warns, and `--witness` reports INVALID for the
records the witness saw. The limits below still apply. Upgrade to 1.1.0.

**Affected:** the `x-omitted` crash is in 1.0.0 and 1.0.1, the heartbeat crash in every release from 0.2.0
to 1.0.1. The others below are in 1.0.1 and, in most cases, earlier releases.

## What was reported

**The verifier could crash instead of giving a verdict.** One record-shaped line, added anywhere in a file,
with a value of the wrong type in `x-omitted` or, on a heartbeat, in `attributes`, ended `mnestiq verify`
with a Python traceback. Anything already found in the file, including real tampering, was not shown. No
signing key was needed, only write access to the file.

**The rules could lose findings without saying so.** When a model call's `context` held a value of the
wrong type, the rules treated it as empty, or skipped the record. Findings that depended on it disappeared
with no notice from the rules. `mnestiq verify` did report the same record as INVALID.

**The threat model was wrong.** `docs/threat-model.md` said a damaged or crafted file meant to crash the
verifier, the rules or the dashboard is reported and that none crashes. That was not true. The test behind
it did not cover optional fields, extension fields, heartbeat records or the dashboard.

## What it did not do

- The reported problems never turned a changed signed record into VALID. In our check of 1.0.1, 4,164
  wrong-type edits of a signed test file gave 4,119 INVALID, 45 crashes and no VALID. All of this is our own
  testing. Other routes can end in VALID: see the top of this note, "Redaction" and "Known limits" below.
- The crash exits non-zero, with the same exit code as INVALID. A script that checks the exit code did not
  accept such a file.
- No evidence is damaged. Removing the added line restores the original file, and it verifies VALID. Until
  that line was removed, the command line gave no verdict and did not say which line was the cause.
- The records stay in the file. The rules' flags and the verdict were affected, not the contents.

## What we found ourselves

**Findings that could be lost on a file that still verifies VALID:**

- A number written differently, such as `4100.0` for `4100`, does not change a record's hash, but it could
  silence a rule that compares the number as text.
- In a very long run, the limit on carried context could cut a call's context short, and the rules did not
  say so.

**Evidence that could be lost or misread while recording:**

- A model could write tool arguments that dropped the record of its own call in the OpenAI integration. A
  prompt injection could use this.
- The API proxy could leave a call out of the evidence when the recorder refused a record, or when the agent
  hung up before the answer started. It could also record a damaged or cut-off answer as a whole one.
- A recorder picking up an existing file did not check the records already signed, and could carry on from
  a file that no longer verified.
- A model reply that failed the SDK's `parse()` lost its text and tool calls from the record.
- A cancelled async model call left no record, and one odd item in a call's history lost the whole call.
- A thread started during a run was not attributed to it, so its connections were not recorded.

**Redaction:**

- `mnestiq redact` copied content held in a field of the wrong shape into the "redacted" file. If you
  redacted a file that does not verify, check the copy.
- Redacting a file with a changed value could produce a copy that verified VALID, because the changed value
  was removed without being checked.

**The signing service:**

- A holder of the service's token could hand the chain over to their own key.
- A repeat request could be used to get the latest position signed again with other values.

**Availability:**

- One bad file could stop the local dashboard listing any file in its folder.
- A small crafted file could make the rules take minutes.
- `inspect` and `redact` could end in a traceback, and `inspect` printed newlines from evidence as new rows.

## What changes in 1.1.0

- Any bad record is an error, the verdict is INVALID, and everything found so far is kept.
- A record or call the rules cannot fully read comes back as a new entry, `MNQ-000 record not evaluated`, in
  `mnestiq.findings` and the dashboard. If your code handles `findings()` by rule id, expect this new id.
- `mnestiq redact` refuses a malformed record, a value that does not match its digest, a field this version
  does not know, and any `x-` field other than `x-omitted`. It writes no copy.
- A recorder refuses to carry on from a file whose chain or signatures do not verify, whether or not `strict` is
  set. Timestamp tokens and key pinning are checked only by `mnestiq verify`. Keep that file as evidence and start
  a new one.
- A recorder that carries on from a file with unsigned records says so in the chain, and `mnestiq verify` adds
  a `signed_after_restart` warning naming those records. A normal crash causes it too.
- With a signer, a close that wrote records adds a `clean_close` heartbeat just before the last checkpoint. A
  recorder that resumes without one says so, and `mnestiq verify` warns `resumed_without_clean_close`. A crash
  right after a checkpoint causes it too, and a file from an older recorder warns once, because older recorders never wrote the mark.
- `Recorder(on_damaged="new_file")`, off by default, needs a `FileSink`. It moves aside a file this recorder cannot
  continue: one that does not verify, or that holds another key or chain. It then starts a new chain, and
  `mnestiq verify` warns `continues_from` on the new chain.
- `mnestiq verify --witness` compares a file with the record the signing service keeps of each chain. A rewritten
  or cut-back file is INVALID, as far as the witness reached. `Recorder(checkpoint_on=...)` can sign right after
  chosen event types.
- `mnestiq verify` refuses a signature or timestamp token in any base64 spelling other than the one a recorder
  writes. Before this, the unused bits of the last character could be changed on the final checkpoint without
  the key. The signed content stayed the same, but the record's hash did not. An empty or null `timestamp_token`,
  or bytes after the token, are errors too.
- `FileSink` refuses anything at the evidence path that is not a regular file: a symbolic link, FIFO, device or
  directory. Before this, crash recovery could cut the last line of the file a link pointed to, and records were
  appended to it. It also refuses to cut a torn line from a file that has another hard link.
- Crash recovery no longer mistakes a record whose own data has a `prev_hash` key for a damaged file.
- `HeadFile` no longer follows a link at its temporary name.
- A model call whose output was not captured, or only partly captured, is reported as `MNQ-000`.
- `create(stream=True)` and the OpenAI stream helpers now record the output. With `instrument_models`, calls
  through `client.post()` and methods replaced on one client are recorded, and a saved `create` or `parse` method
  is recorded too. A saved `client.request` method is not.
- Python audit hooks record connections the patches missed, datagrams, name lookups and process launches during
  a run. Through a proxy, `host` is the real destination, and an ignored name no longer hides a connection to a
  proxy that is not ignored. `MNQ-003` also fires on a noted datagram or raw socket. Each destination is noted once
  before and once after untrusted content first reaches the model, up to 256 per kind each time. Past the limit after that
  point, the rules report `MNQ-000` rather than naming the destination.
- With `instrument_egress()`, threads and thread pool tasks started during a run belong to it. `urllib` and
  `urllib3` are recorded, and stamped only for hosts in `stamp_hosts`. Asyncio connections on Windows are recorded.
- New options: `mnestiq.instrument_models(recorder)` records calls through the Anthropic and OpenAI SDKs without
  wrapping each client, and `mnestiq signer serve --azure-key` puts the signing service's rules in front of
  Azure Key Vault. `AzureKeyVaultSigner` was tested against real Azure on 2026-10-07. The service in front of it
  has been tested against a stand-in only.
- The signing service refuses a hand-over to another key unless started with
  `mnestiq signer serve --allow-handover`. A repeat must be identical to the original request.
- The `error` field follows `max_content_bytes`.
- A line that is anything but valid JSON or JSON whitespace is an error. So are numbers too large to keep,
  such as `1e999`.

The record format and spec version are unchanged. One rule for reading checkpoints is stricter: a signature or
timestamp token must be spelled as a recorder writes it. An empty or null `timestamp_token`, or bytes after the
token, are errors too.

## Known limits

These remain, and `docs/threat-model.md` states them:

- An edit of the right type, such as an emptied `context`, cannot be told apart by the rules. Only
  `mnestiq verify` shows it, so read findings together with the verdict.
- A file cut back to a checkpoint verifies on its own. Keep a head elsewhere, use the vault, or use
  `--witness`. A cut back to a point right after an earlier clean close gives no restart warning.
- Records after the last signature have only the hash chain. Someone with write access can rewrite them and
  redo the hashes, and a recorder that then carries on from the file signs over them. The file verifies VALID
  with a `signed_after_restart` warning. If every unsigned record is removed and a recorder restarts,
  `mnestiq verify` warns `resumed_without_clean_close`. `--witness` turns these into INVALID, for the records
  the witness saw. Direct use of Key Vault has no witness, and a holder of the service's token can mislead it.
  Frequent checkpoints keep that window short.
- Emptying or replacing a whole file starts a chain that looks clean, unless a head or the vault says otherwise.
  `--witness` cannot show it.
- Capture runs inside the agent's Python process, and code in that process can work against it. Native
  extensions with their own sockets, `uvloop`, and the network traffic of child processes that are not Python
  are not seen. Bare secrets passed as positional arguments to a process are not masked.
- `system_prompt_hash` has no salt and stays after redaction, so a guessed system prompt can be confirmed.
- The timestamp on the last checkpoint is outside what is signed and can be removed. `--head` catches it.
- A record's hash covers its canonical form. Respelling a number (`5` as `5.0`), changing the key order or JSON
  spacing, or writing a character as an escape (`\u0061`) leaves the hash the same.
- Whoever holds the signing key can sign a rewrite. With direct use of Key Vault, so can someone in control of an
  identity allowed to sign. Only a copy kept elsewhere shows it.

`docs/claims-map.md` lists the security claims we took from our documents and the test behind each one. It does
not cover every sentence.

## What to do

Upgrade. If `mnestiq verify` ended in a traceback on a file you care about, treat that file as suspect and
verify it again with 1.1.0. If you hand chains over through the signing service, add `--allow-handover`. A
Mnestiq Workbench release that requires 1.1.0 will follow.
